# ゲームの爽快感・達成感（game feel）

調査レポート「ゲームの爽快感・達成感 調査」（2026-11-26）を、100games の制作で使える形にまとめたもの。
出典・事例の詳細は [references/research.md](references/research.md)、実装コード例は [references/snippets.md](references/snippets.md) を参照。

> 数値の目安は講演・二次資料で一般に語られる範囲の**初期値**であり、出典の一次確認やプレイ検証を経たものではない。必ず自分のゲームで遊んで調整する。

## 1. 爽快感・達成感の7要素

新しいゲームを作るときは、まず「どの要素で気持ちよくするか」を決める。演出は、それぞれの要素に役立つ分だけ足す。

| # | 要素 | 中身 | 効くもの |
|---|---|---|---|
| 1 | **即時・多重フィードバック** | 入力した瞬間に音・動き・光が返る（juice / 手ごたえ） | 爽快感の核 |
| 2 | **痕跡が残る可視的変化** | 触った場所の状態が目に見えて変わり、その変化が残る（ビフォー／アフター） | 爽快感・達成の「証拠」 |
| 3 | **小さな完了の連鎖** | 1秒〜数十秒ごとに「できた」が音や表示で確定する | 達成感の核 |
| 4 | **入力に対する出力の大きさ** | 小さな操作で、大量・広範囲・派手な結果が出る（無双 / Vampire Survivors 型） | 爽快感 |
| 5 | **課題と技能の釣り合い** | 少し難しいができそう。リスクのすぐ隣にリターンがある | 達成感・フロー |
| 6 | **自分のペースと選択** | 順序や休むタイミングを選べ、失敗の罰が軽い（自律性） | 心地よさ・継続 |
| 7 | **成長の可視化** | 道具・範囲・速度・自分の腕が前より上がったと分かる | 達成感の持続・もう1回 |

**最重要ルール**：小さなゲームでは、まず **1（即時フィードバック）＋2（痕跡）＋3（進捗表示と完了音）** の3つを徹底する。4〜7 はその上に積む増幅器であり、土台がないままコンボや成長を入れても効かない。

## 2. 制作の手順

1. **快感の核を1文で書く**。例：「なぞった所の色が一気に塗り替わるのが気持ちいい」。題材が現実の作業なら、面倒な部分（準備・後片付け・疲労・コスト・やり直し不可）を全部削り、「作用 → 即時の変化」という核だけを残す（PowerWash Simulator の考え方）。
2. **土台を先に作る：制御 → 空間 → 演出の順**。入力遅延・移動の重さや慣性がおかしいと、パーティクルを足しても気持ちよくならない。演出で遅延をごまかさない。
3. **P0 を全部満たす**（下のチェックリスト）。
4. **演出は1つずつ足す**：「1テクニック追加 → 遊ぶ → 残すか捨てるか決める」を繰り返す。まとめて入れない。
5. **引き算する**：何が起きたか分かりにくくなった演出、視認性や因果関係を損なう演出は削る。
6. ゲームの `README.md` の「学んだこと」に、どの要素を狙い、何を足して何を削ったかを書く。

## 3. 「盛りすぎ」は逆効果（逆U字）

Kao (2020) の研究では、juice（演出量）を None / Medium / High / Extreme の4段階で比べ、**Medium と High が None と Extreme の両方を上回った**と報告されている（二次要約経由）。演出は「何が起きたかがより明確になる」範囲でだけ足す。

## 4. テクニック集（初期値と、やりすぎたときの害）

| テクニック | 要素 | 実装の目安（初期値） | やりすぎると |
|---|---|---|---|
| 即時フィードバック | 1 | 入力した同フレーム〜数十ms以内に、何らかの見た目か音の変化を返す | 遅延を演出でごまかすと、かえって嘘っぽくなる。まず遅延を直す |
| ヒットストップ | 1,3 | 小：30〜60ms ／ 決定的な瞬間：100〜200ms ／ ボス級：それ以上＋フラッシュ。段階は「止め → 止め＋揺れ → 止め＋揺れ＋スロー」 | 頻発するとカクつきやラグに見える。連続作業の最中には入れない |
| 画面シェイク（trauma 方式） | 1,4 | 揺れ量 ＝ trauma² で、時間とともに減衰させる。小さな出来事では微量にする | 常に揺れていると酔い、視認性が落ちる。何が当たったか分からなくなる |
| パーティクル＋残留物 | 1,2 | 破片を飛ばし、しばらく地面に残す（permanence）。残った破片が「自分の仕事の跡」になる | 数が多すぎると処理落ちし、画面がノイズだらけになる |
| 効果音の重ね・ピッチ変化 | 1,3 | 連打する音はピッチを ±数% ランダムに、連続時は上昇させる。基本は低音（衝撃）＋高音（きらめき）の2層。環境音のループと出来事の音は別系統にする | 同じ音の単調な連打は、疲れる原因の筆頭 |
| 完了音（DING 型） | 3 | ある単位が **100% になった瞬間だけ**、短く明るい確定音を鳴らす。1プレイで何回鳴るかをレベル設計の段階で決める | 鳴りすぎると価値が下がる。99% では鳴らさない |
| コンボ／チェーン | 4,5 | 連続で処理すると倍率・速度・範囲が上がる。途切れる条件は「止まる」「一定時間何もしない」だけにする | 維持がノルマになると要素6（自分のペース）が壊れる。コンボはご褒美であってノルマにしない |
| 進捗の常時表示 | 2,3,7 | 全体の%と、今いる単位の%を二重に表示する。残りが少ないほど目立たせる | 数字が大きすぎるとノルマ感が出る。序盤は空間の変化を主、数字を従にする |
| 領域の塗り替え | 2 | 処理済みの領域は、色・高さ・質感を未処理と明確に変える。境界のエッジをくっきりさせる | 差が弱いと「やった感」が消える。チカチカするなら、彩度ではなく明度や質感で差を作る |
| イージング／squash & stretch | 1 | 線形の動きをやめる。UI の数字やゲージもイージングで増やす | 全部ふにゃふにゃだと操作が不正確になる。操作系には弱く、演出系には強くかける |
| 段階的な解放・成長 | 7,4 | 処理量に応じて範囲・速度・同時処理数を段階的に解放する。各段階で「さっきできなかったこと」を1つできるようにする（塊魂型） | 速すぎると課題が消え、遅すぎると単調になる。成長のたびにフィールドも広く・密にする |
| カメラの追従・先行 | 1 | カメラは少し遅れて滑らかに追い（lerp）、移動方向へわずかに先行させる | 遅延が大きいと酔う。固定画面のゲームなら入れなくてよい |
| 失敗の軽さ・即リトライ | 6,5 | 失敗しても稼いだ分は消さない（Hades 型）。リトライは1入力で即時に | 罰がゼロだと緊張もゼロ。罰の代わりに自己ベストや美しさの評価で手応えを作る |
| 選択の自由 | 6 | 処理する順序をプレイヤーに任せる | 目標が曖昧になる。「おすすめの次」を薄く示して両立させる |
| 音の音楽化 | 1,5 | 出来事の音のピッチを音階に量子化し、連続処理が自然にメロディになるようにする（テトリスエフェクト型） | 音の判別（高い音＝良いこと、など）が弱まる。判別用の音色差は残す |

## 5. 設計の原則（事例から）

- **リスクとリターンは近くに、比例した大きさで置く**（桜井政博）。危険のすぐ隣に報酬を置く。意図的に低リスクにする設計（カービィ）も、対象層を狙ったものなら正解。
- **入力1回あたりの出力を増幅する**（無双、Vampire Survivors）。爽快さを決めるのは敵の強さではなく、**対象の密度と、一度に薙ぎ払える単位**。まばらな対象を1つずつ処理する設計は、その逆になる。
- **自己増殖ループ**（塊魂）。処理できる対象のサイズや量が、処理した分だけ増える。
- **作業系では敵や制限時間を本編に入れない**（PowerWash）。入れるならチャレンジモードとして分ける。
- **完了の単位を小さく分割する**（PowerWash の DING、Celeste の1画面、テトリスの1ライン）。完了する頻度が、そのまま「もう少しやろう」の頻度になる。
- **ビフォー／アフターのコントラストは劇的に**。美しさより先に**判別しやすさ**を最大化する。
- **失敗の痛みを構造で抜く**（Hades）。負けても物語・強化・記録が前進する。
- **難易度は軸ごとに分ける**（Celeste の Assist Mode）。速度・無敵・制限時間などを個別にオン／オフできるようにし、判断的な名前（「チート」など）は付けない。
- **前進が得になる動線**（DOOM の push forward）。止まると損、進み続けると得、にする。
- **現実の作業にないものを足す**：現実より速く・広く処理できる、「100%」という到達できる完了がある、世界が自分の仕事を覚えている。
- **スロット由来の演出は「音と演出の密度」だけ借りる**。ランダムな課金や射幸心を煽る仕組みとは結びつけない。
- **フロー**は、明確な目標・測定できる進捗・即時で曖昧でないフィードバック・自分で制御できる感覚から生まれる。低リスクのゲームでは、難易度ではなく効率・残量の減る速さ・自己ベストで課題を作る。
- **SDT（自己決定理論）**：有能感（習得しやすい操作・明確なフィードバック）、自律性（選択・自分のペース）、関係性（共有・協力。小さなゲームでは省略してよい）。

## 6. 実装チェックリスト

### P0：これがないと始まらない
- [ ] 入力への反応に遅延がない（移動と判定を同じフレームで返す）
- [ ] 処理した場所の見た目が、未処理とはっきり違う
- [ ] アクションのたびに音が鳴る（連打に耐えるよう、ピッチをランダム化する）
- [ ] 進捗（%・残量・スコア）が常に見える
- [ ] 小さな完了の単位を決め、完了時に確定音と表示を出す
- [ ] 失敗しても積み上げが消えない／作業系なら制限時間をデフォルトにしない
- [ ] 最初のステージは数分で完了できる大きさにする

### P1：爽快感を増幅する
- [ ] 破片パーティクルと、数秒の残留
- [ ] 抵抗 → 解放の手ごたえ（触れた瞬間のわずかな減速 → 処理した瞬間に軽くなる）
- [ ] 罰のないコンボ
- [ ] 完了の瞬間だけ、小さなヒットストップとフラッシュ
- [ ] 段階的な成長（数値の増加だけでなく、新しい気持ちよさを1つ足す）

### P2：達成感を持続させ、深める
- [ ] 美しさなど、任意の評価
- [ ] 自己ベスト（最速・最大コンボ・パーフェクト回数）を `shared/storage.js` で保存する
- [ ] 音階に量子化した効果音
- [ ] チャレンジモード（制限時間あり）を本編と分ける
- [ ] 軸ごとの支援オプション

### ✕ アンチパターン
- 画面シェイクとパーティクルを「とにかく全部」盛る
- 完了音を頻発させて価値を薄める
- コンボの維持をノルマにする
- 演出で遅延をごまかす
- 序盤から広すぎるフィールドを出す（完了が遠すぎてフローにならない）

## 7. レビューするとき

既存のゲームを見るときは、7要素それぞれについて「ある／弱い／ない」を判定する。P0 の欠けを最優先で報告し、次に「盛りすぎ」（視認性・因果関係を壊している演出）を指摘する。改善案は1度に1〜2個に絞り、「足したら遊んで確かめる」前提で出す。
